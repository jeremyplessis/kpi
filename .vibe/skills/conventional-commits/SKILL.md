# Conventional Commits pour le projet KPI

Ce skill t'aide à rédiger des messages de commit et de pull requests conformes à la convention Conventional Commits, adaptée aux spécificités du projet KPI.

## Contexte du projet

Le projet KPI suit une feuille de route structurée avec des étapes claires (1-6). Les commits doivent refléter cette structure et utiliser les types et scopes appropriés.

## Règles générales

### Format du message de commit

```
<type>([scope]): <description>

[corps optionnel]

[footer optionnel]
```

### Types de commits autorisés

| Type | Description | Quand l'utiliser |
|------|-------------|-------------------|
| `feat` | Nouvelle fonctionnalité | Ajout d'une fonctionnalité visible par l'utilisateur |
| `fix` | Correction de bug | Correction d'un comportement incorrect |
| `docs` | Documentation | Ajout ou modification de documentation |
| `style` | Style | Modifications de formatage, espaces, etc. sans impact fonctionnel |
| `refactor` | Refactoring | Modification du code sans changer le comportement |
| `test` | Tests | Ajout ou modification de tests |
| `chore` | Maintenance | Mise à jour de configuration, dépendances, etc. |
| `perf` | Performance | Optimisation de performance |
| `build` | Build | Modifications des fichiers de build (pyproject.toml, etc.) |

### Scopes spécifiques au projet KPI

| Scope | Composant | Exemple |
|-------|-----------|---------|
| `bdd` | Base de données et repositories | `feat(bdd): ajouter index sur suivi_activite.date` |
| `kpi` | Moteur de calcul des indicateurs | `fix(kpi): corriger le calcul du taux de ghosting` |
| `web` | Application web (FastAPI, templates) | `feat(web): ajouter l'écran de consultation` |
| `import` | Outil d'import initial | `fix(import): corriger la lecture des dates Excel` |
| `ga` | Connecteur Google Analytics | `feat(ga): implémenter l'API GA4` |
| `pdf` | Génération de PDF | `feat(pdf): ajouter export WeasyPrint` |

### Scopes optionnels

Les scopes sont optionnels mais **fortement recommandés** pour le projet KPI afin de faciliter le suivi des changements par composant.

## Exemples de messages de commit

### Nouvelle fonctionnalité

```bash
# Ajout d'une nouvelle fonctionnalité complète
feat(web): ajouter l'écran de consultation des KPI

Implémente les routes pour afficher les indicateurs avec :
- Filtres par période (année, mois, personnalisé)
- Affichage des cartes de synthèse
- Intégration de Chart.js pour les graphiques

Clôt l'étape 4 de la feuille de route.

Generated by Mistral Vibe.
Co-Authored-By: Mistral Vibe <vibe@mistral.ai>

# Ajout d'un indicateur
feat(kpi): implémenter l'indicateur RDV par canal

Ajoute la classe RdvParCanal qui compte les rendez-vous
par année et canal de réponse.

# Ajout d'une table de référence
feat(bdd): ajouter la table de référence provenance

Crée la table et l'intégrer dans le Repository.
```

### Correction de bug

```bash
# Correction simple
fix(kpi): corriger le calcul du taux de ghosting

Le taux était calculé sans dédoublonnage des réponses.
Maintenant conforme aux règles validées du 28/10/2026.

# Correction avec contexte
fix(web): empêcher la soumission du formulaire vide

Ajoute une validation côté serveur pour vérifier
que le champ personne n'est pas vide.

# Correction urgente
fix!: corriger l'import qui écrasait les données existantes

BREAKING CHANGE: l'option --force est maintenant requise
pour supprimer les données existantes avant import.
```

### Documentation

```bash
# Documentation utilisateur
docs: ajouter le guide de l'écran de saisie

Documentation complète de l'écran de saisie avec :
- Parcours utilisateur
- Explications des champs
- Capture d'écran

# Documentation technique
docs: documenter le pattern Repository

Ajoute une section dans l'architecture expliquant
le rôle de chaque Repository.

# Mise à jour du README
docs: mettre à jour la feuille de route

Marque l'étape 3 comme terminée et ajoute les détails
pour l'étape 4.
```

### Refactoring

```bash
# Refactoring simple
refactor(bdd): extraire la logique de dédoublonnage

Crée une méthode _dedoublonner_par_mois dans SuiviRepository
pour centraliser la logique utilisée par plusieurs indicateurs.

# Refactoring majeur
refactor(web): réorganiser les routes par domaine

Réorganise les routes dans routes.py par groupe logique :
- Routes de saisie
- Routes de consultation
- Routes de configuration

# Refactoring avec amélioration
refactor(kpi)!: simplifier l'API des indicateurs

BREAKING CHANGE: la méthode calculer() retourne maintenant
un objet ResultatIndicateur au lieu d'une liste brute.

# Refactoring de tests
refactor(tests): utiliser des fixtures communes

Extraire les jeux de données tests dans des fixtures
pour éviter la duplication.
```

### Tests

```bash
# Ajout de tests
test(kpi): ajouter des tests pour NbDemandes

Tests unitaires pour vérifier le dédoublonnage par
(mois, personne) conformément aux règles métiers.

# Correction de tests
test: corriger les tests qui échouaient avec Python 3.14

Mise à jour des imports pour compatibilité 3.14.

# Tests d'intégration
test(web): ajouter des tests pour les routes de consultation

Tests avec httpx pour vérifier le bon fonctionnement
des endpoints /kpi/*
```

### Maintenance

```bash
# Mise à jour de dépendances
chore: mettre à jour les dépendances

- openpyxl: 3.1.0 → 3.1.2
- fastapi: 0.115.0 → 0.115.1

# Configuration
build: ajouter httpx comme dépendance de développement

Nécessaire pour les tests de l'application web.

# Nettoyage
chore: supprimer le code commenté inutilisé

Nettoyage des fichiers sources selon PEP 8.
```

### Performance

```bash
# Optimisation SQL
perf(bdd): ajouter des index sur les colonnes fréquemment filtrées

Ajoute des index sur :
- suivi_activite.date
- suivi_activite.personne_id
- suivi_activite.canal_id

# Optimisation de calcul
perf(kpi): optimiser le calcul du taux de ghosting

Remplace la boucle O(n²) par une approche O(n)
avec des dictionaries.
```

## Règles spécifiques au projet KPI

### 1. Référencer les étapes de la feuille de route

Quand un commit clôt une étape ou une partie d'une étape, mentionnez-le dans le corps ou le footer :

```bash
feat(web): implémenter l'écran de saisie

Clôt l'étape 3 de la feuille de route.

fix(kpi): corriger les calculs validés le 28/10/2026

Conforme aux règles documentées dans 
01_proposition_architecture.md
```

### 2. Mentionner les règles métiers

Quand un commit modifie une règle métier (ex: calcul des indicateurs), toujours référencer :
- La date de validation de la règle
- Le document où elle est documentée

```bash
fix(kpi): corriger la règle de réponse pour le ghosting

La règle validée le 28/10/2026 indique que "Relance"
est une action du photographe, pas une réponse du contact.

Voir documentation/01_proposition_architecture.md
```

### 3. Scopes obligatoires pour certains types

| Type | Scope obligatoire ? | Raison |
|------|---------------------|--------|
| `feat` | ✅ Oui | Pour identifier quel composant a été ajouté |
| `fix` | ✅ Oui | Pour identifier quel composant a été corrigé |
| `refactor` | ✅ Oui | Pour identifier quel composant a été restructuré |
| `perf` | ✅ Oui | Pour identifier quel composant a été optimisé |
| `test` | ❌ Non | Les tests couvrent généralement plusieurs composants |
| `docs` | ❌ Non | La documentation peut couvrir plusieurs sujets |
| `style` | ❌ Non | Les modifications de style sont généralement globales |
| `chore` | ❌ Non | Les tâches de maintenance sont généralement globales |
| `build` | ❌ Non | Les modifications de build sont généralement globales |

### 4. Utilisation de BREAKING CHANGE

Utilisez `!` après le type et ajoutez un footer `BREAKING CHANGE:` quand :
- Le schéma de la base de données change de manière incompatible
- L'API d'une classe publique change
- Le comportement d'un indicateur change
- Le format des données d'import change

```bash
feat(bdd)!: ajouter la colonne entreprise_id à personne

BREAKING CHANGE: les scripts qui accèdent directement
à la table personne doivent être mis à jour.

Migration requise : ALTER TABLE personne ADD COLUMN entreprise_id INTEGER
```

## Messages de Pull Request

### Format du titre

Même format que les commits : `<type>([scope]): <description>`

### Structure de la description

```markdown
## Description

[Description concise des changements]

## Contexte

[Pourquoi ces changements sont nécessaires]
[Lien vers l'issue ou le ticket si applicable]

## Changements apportés

- [x] Nouvelle fonctionnalité
- [x] Correction de bug
- [ ] Refactoring
- [ ] Documentation
- [x] Tests

## Tests

- [x] Tous les tests existants passent (`python -m unittest discover -s tests`)
- [x] Nouveaux tests ajoutés pour les nouvelles fonctionnalités
- [x] Testé manuellement sur les données réelles

## Documentation

- [x] README.md mis à jour
- [ ] Documentation utilisateur mise à jour
- [x] Documentation technique mise à jour

## Vérification

- [x] Respecte les conventions de code (PEP 8)
- [x] Respecte Conventional Commits
- [x] Pas de données réelles commitées
- [x] Tous les commits sont signés
```

### Exemples de Pull Request

#### Nouvelle fonctionnalité

```markdown
## feat(web): implémenter l'écran de consultation des KPI

## Description

Ajoute l'écran de consultation des indicateurs avec :
- Sélecteur de période (année, mois, personnalisé)
- Cartes de synthèse pour chaque KPI
- Graphiques interactifs avec Chart.js
- Export PDF via WeasyPrint

## Contexte

Clôt l'étape 4 de la feuille de route. Permet à l'utilisatrice de consulter
ses indicateurs sans avoir à utiliser le classeur Excel.

## Changements apportés

- [x] Nouvelle fonctionnalité
- [x] Tests
- [x] Documentation

## Tests

- [x] Tous les tests existants passent
- [x] Tests unitaires pour les nouveaux indicateurs
- [x] Tests d'intégration pour les nouvelles routes
- [x] Testé manuellement

## Documentation

- [x] README.md mis à jour (section mise en route)
- [x] documentation/04_ecran_consultation.md créé
```

#### Correction de bug

```markdown
## fix(kpi): corriger le calcul du taux de ghosting

## Description

Corrige le calcul du taux de ghosting qui ne dédoublonnait pas correctement
les réponses par personne et par mois.

## Contexte

Problème identifié lors des tests avec les données réelles : certaines personnes
apparaissaient comme ayant répondu plusieurs fois dans le même mois, faussant
le calcul du taux.

Règle validée le 28/10/2026 : une personne ne compte qu'une fois par mois pour
les demandes et une fois par mois pour les réponses.

## Changements apportés

- [x] Correction de bug
- [x] Tests

## Tests

- [x] Tous les tests existants passent
- [x] Test spécifique ajouté pour ce cas
- [x] Vérifié avec les données réelles

## Documentation

- [ ] Pas de documentation à mettre à jour
```

## Vérification des commits

Avant de créer une PR, vérifiez que tous les commits respectent Conventional Commits :

```bash
# Voir l'historique des commits
git log --oneline

# Vérifier un commit spécifique
git show <hash>
```

Si un commit ne respecte pas la convention, utilisez `git commit --amend` pour le corriger.

## Outils utiles

### Vérification automatique

Vous pouvez utiliser des outils comme `commitlint` pour vérifier vos messages :

```bash
# Installation
npm install -g @commitlint/cli @commitlint/config-conventional

# Vérification
commitlint -e <message-de-commit>
```

### Template de commit

Ajoutez ce template à votre `.git/config` pour vous aider :

```gitconfig
[commit]
    template = ~/.gitmessage
```

Avec le contenu suivant dans `~/.gitmessage` :

```
# <type>([scope]): <description>
#
# [Corps optionnel : pourquoi ce changement ?]
#
# [Footer optionnel : issues, BREAKING CHANGE, etc.]
#
# Types : feat, fix, docs, style, refactor, test, chore, perf, build
# Scopes : bdd, kpi, web, import, ga, pdf
#
# Exemple : feat(web): ajouter l'écran de consultation
```

## Erreurs courantes à éviter

### ❌ Messages trop vagues

```bash
# ❌ Mauvaise pratique
fix: corriger le bug

# ✅ Bonne pratique
fix(kpi): corriger le calcul du taux de ghosting pour janvier 2025
```

### ❌ Messages trop longs dans la ligne de sujet

```bash
# ❌ Mauvaise pratique (trop long)
feat: implémenter l'écran de consultation des KPI avec graphiques et export PDF

# ✅ Bonne pratique
feat(web): implémenter l'écran de consultation des KPI

Implémente les graphiques avec Chart.js et l'export PDF avec WeasyPrint.
```

### ❌ Oublier le scope quand il est nécessaire

```bash
# ❌ Mauvaise pratique (scope manquant)
feat: ajouter un nouvel indicateur

# ✅ Bonne pratique
feat(kpi): ajouter l'indicateur NbProspects
```

### ❌ Utiliser le passé au lieu de l'impératif

```bash
# ❌ Mauvaise pratique (passé)
fix: j'ai corrigé le bug

# ✅ Bonne pratique (impératif)
fix: corriger le bug
```

### ❌ Oublier de documenter les BREAKING CHANGES

```bash
# ❌ Mauvaise pratique
feat(bdd): ajouter entreprise_id à personne

# ✅ Bonne pratique
feat(bdd)!: ajouter entreprise_id à personne

BREAKING CHANGE: migration requise pour les bases existantes.
```

## Résumé rapide

| Situation | Format | Exemple |
|-----------|--------|---------|
| Nouvelle fonctionnalité | `feat(scope): description` | `feat(web): ajouter l'écran de consultation` |
| Correction de bug | `fix(scope): description` | `fix(kpi): corriger le calcul du ghosting` |
| Documentation | `docs: description` | `docs: mettre à jour le README` |
| Refactoring | `refactor(scope): description` | `refactor(bdd): extraire le Repository pattern` |
| Tests | `test(scope): description` | `test(kpi): ajouter tests pour NbDemandes` |
| Maintenance | `chore: description` | `chore: mettre à jour les dépendances` |
| BREAKING CHANGE | `type(scope)!: description` | `feat(bdd)!: modifier le schéma` |
